# 「麦当劳营养王国」预研与可行性分析

> 预研日期：2026-10-20 ｜ 大赛截止：2026-10-25（**仅剩 5 天**）
> 结论先行：**四个想法里，"潮玩/积分"可行性最高且 MCP 完全支撑，可赶在大赛前落地；"许愿"有两条落地路径，其中"即时实现"可行、"收集提交"受限于无官方接口；"点餐"是地基，继续做强。**

---

## 一、现状盘点

当前项目已实现「营养点餐」全链路，但 **MCP 有 30+ 工具，我们只用了约 8 个**。大量现成能力尚未挖掘，这正是"王国"扩大的弹药。

| 维度 | 现状 |
|------|------|
| 已实现 | 营养拼配（3 模式 + 忌口 + 全天规划）+ 门店 → 映射 → 算价 → 下单 |
| 已用工具 | `list-nutrition-foods`、`query-nearby-stores`、`query-meals`、`calculate-price`、`create-order`、`query-order`、`query-store-coupons`、`query-my-account`(规划) |
| 未用但可用的工具 | 积分商城（实物/周边）、抽奖、奖品、活动日历、派对预订、优惠券领取、团餐、外送地址等 **约 20+ 个** |

**关键发现**：麦当劳 MCP 本身就是一个"营养 + 积分 + 潮玩 + 派对"的完整生态接口，我们的"营养王国"概念与官方能力高度对齐，不是空想。

---

## 二、四个想法逐项分析

### 想法 1️⃣ 点餐（现有功能）

| 项 | 结论 |
|----|------|
| 可行性 | ✅ 已落地 |
| 定位 | "王国"的地基，其余模块都从点餐延伸 |
| 建议 | 保持现有核心，新增"叠券省钱""积分抵扣"等入口与之联动 |

### 想法 2️⃣ 许愿（Wish）—— 小孩 / 爱美女性的高要求

**核心结论**：MCP **没有**"提交愿望"的官方接口，但有两条可落地的路径，且有一个隐藏的"体验型愿望"入口（派对类目）。

#### 路径 A：Agent 即时实现（可行度 ★★★★☆）
把"愿望"解析成营养/口味约束，交给现有引擎直接实现。
- 例：小孩说"我想吃一个不辣、有玩具、甜甜的儿童套餐" → 解析为 `exclude=["辣"]` + 儿童套餐类 + 甜点，直接拼出。
- 例：爱美女性说"我想吃一顿不胖、高蛋白、还要好吃不会长痘的" → 解析为 `lowcarb/protein` + `exclude=["油炸"]`。
- **难点**：自然语言 → 结构化约束的语义解析（这是真正的技术亮点，适合作为"演示彩蛋"）。

#### 路径 B：无法实现的愿望 → 收集 → 提交麦当劳（可行度 ★★★☆☆）
- 无法实现（如"想要低卡版的麦辣鸡腿堡""想要纯素巨无霸"）→ 存入本地愿望池（JSON）→ 汇总导出。
- 提交渠道：**无官方 API**，只能走非结构化渠道（邮箱 / 飞书 / 问卷）。当前 `agent-mail`、`飞书` 连接器均可用，可一键把愿望清单发到指定邮箱或飞书群。
- **风险**：愿望含用户信息，需走合规声明（延续 CONTEST_DECLARATION 的敏感信息原则）。

#### 隐藏加分项：派对 = "体验型愿望"（可行度 ★★★★★）
MCP 的派对类目**本质就是愿望落地**：生日派对、主题派对、麦麦体验营、品鉴会、读书会、过家家派对（实测活动日历里就有"过家家派对""趣读派对"）。
- 工具：`query-party-city → query-party-store → query-party-store-date → query-party-store-session → party-order-create`，全链路可预订。
- 对小孩/亲子场景是绝配，可作为"许愿"的**可下单落点**。

### 想法 3️⃣ 潮玩元素（积分兑换潮玩实物 + UI 潮玩）

**核心结论：可行性 ★★★★★，MCP 完全支撑，实测已通。**

实测调用结果（真实数据，非 mock）：

| 能力 | 工具 | 实测返回 |
|------|------|----------|
| 积分商城实物/周边 | `mall-points-products` | Nike Book 2 麦当劳联名款（8888 积分）、罗技键鼠套装（6666 积分）、酸黄瓜吧唧礼盒（800 积分） |
| 积分抽奖 | `query-lottery-info` | "麦麦积分抽奖"进行中，24 积分/次，奖品含优惠券 + 30 积分 |
| 积分账户 | `query-my-account` | 麦享会积分（可用/累计/本月过期等字段齐全） |
| 我的奖品 | `query-my-prizes` | 中奖记录（可用/已用/过期状态） |
| 联名潮玩活动 | `campaign-calendar` | PEACEMINUSONE 联名棒球帽/徽章/丝巾、"任意餐品 +39.9 元得周边""积分抢先购" |

#### 落地建议
1. **「积分中心」模块**：查积分 → 逛商城 → 兑实物/周边 → 抽奖 → 查奖品，一条龙。
2. **UI 潮玩元素**：周边橱窗卡片流、联名色系、抽奖转盘/盲盒感、积分"数字藏品"式展示。当前 Web 是单文件自包含，加一个"潮玩宫" tab 即可。
3. **联名热点**：活动日历实时返回当季联名（如 GD/PEACEMINUSONE），可作为"潮玩宫"的滚动横幅。

#### 风险
- 积分兑换/抽奖是**有副作用的真实操作**（`mall-create-order`、`draw-lottery`），必须用户确认。
- 实物**限量**（如"每日限量 5 份"），需处理"售罄"状态（`status=3`）。
- 测试账号积分=0，演示时需讲清"攒积分→点餐→兑换"的闭环故事，而非直接展示兑换成功。

### 想法 4️⃣ 其他建议

| 建议 | 工具支撑 | 价值 | 优先级 |
|------|----------|------|--------|
| A. 派对/亲子场景 | `query-party-*` + `party-order-create` | 覆盖小孩用户群，与"许愿"协同 | ⭐⭐⭐ |
| B. 优惠券省钱助手 | `available-coupons`/`auto-bind-coupons`/`query-my-coupons` | 点餐时自动叠券，实用性强 | ⭐⭐⭐ |
| C. 活动日历入口 | `campaign-calendar` | "今天有什么联名/活动"当首页入口 | ⭐⭐⭐ |
| D. 企业团餐 | `query-promotions`/`query-meal-assistance`（beType=6） | 拓展 B 端，差异化亮点 | ⭐⭐ |
| E. 外送地址管理 | `delivery-*` | 补齐外送全链路 | ⭐⭐ |

## 三、可行性总评

| 想法 | 可行性 | 技术难度 | MCP 支撑 | 大赛前可落地 | 建议 |
|------|:---:|:---:|:---:|:---:|------|
| 1 点餐 | ✅ 已落地 | 低 | 完整 | — | 做强，与各模块联动 |
| 2 许愿（即时实现） | 高 | 中 | 间接 | ✅ 演示级 | 语义解析做彩蛋 |
| 2 许愿（收集提交） | 中 | 低 | 无接口 | ✅ 演示级 | 本地池 + 邮件/飞书导出 |
| 2 许愿（派对预订） | 高 | 中 | 完整 | ⚠️ 规划级 | 读链路可演示，下单需确认 |
| 3 潮玩/积分 | **最高** | 低 | **完整** | ✅ 完全可落地 | 优先做 |
| 4 优惠券/活动/团餐 | 高 | 低-中 | 完整 | ✅ 优惠券+活动可落地 | 按需 |

**总体判断**："麦当劳营养王国"概念成立，且大部分有 MCP 硬支撑。真正的限制不是技术，而是 **5 天时间**——因此需分清"提交版落地"与"愿景规划"。

## 六、风险与合规提示

1. **副作用操作确认**：`create-order`、`mall-create-order`、`draw-lottery` 均需用户明确确认（沿用现有 v2 下单的确认机制）。
2. **积分=0 的演示问题**：测试账号可用积分为 0，需设计"攒积分"叙事闭环。
3. **许愿隐私合规**：收集愿望即收集用户表达，需延续敏感信息声明，仓库不存真实凭证/个人信息。
4. **潮玩图片外链**：周边图来自 `img.mcd.cn` / `cms-cdn.mcd.cn`，离线演示需本地兜底图（沿用快照兜底思路）。
5. **限量/售罄状态**：实物兑换有"每日限量、先到先得"，需处理 `status` 字段。
